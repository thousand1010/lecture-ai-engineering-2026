# 第1回 発展：応答時間・トークン数の比較

## 現状と追加した機能

既存の `app.ask` は、会話履歴を保った連続質問と、今回／セッション累計の入力・出力トークン表示に対応している。ここに各 API 呼び出しの応答時間表示を追加した。

モデル間の比較には `app.benchmark` を使う。比較時は毎回履歴なしの独立した質問を送り、過去の会話による入力長の差を避ける。モデル×質問の各組み合わせを既定で3回計測し、結果を1リクエストずつCSVに保存する。コンソールには成功数、429の回数、応答時間の平均・中央値、各トークン数の平均を表示する。

## 実行手順

通常の会話でも応答時間を確認できる。

```bash
uv run python -m app.ask "LoRAとは何ですか？"
```

比較例（2モデル×既定3問×3回＝18リクエスト）：

```bash
uv run python -m app.benchmark \
  --models gemini-3.5-flash-lite gemini-3.1-flash-lite \
  --repeat 3 \
  --interval 15 \
  --output results/lec01-comparison.csv
```

モデル名は利用時のAI Studioで使えるものに置き換える。`--models` を省略すると、`AIE_MODEL` 環境変数（未設定時は講座の既定モデル）を使う。既定の質問は、LoRAの短い説明、講座固有の宿題に関する質問、RAGとファインチューニングの詳しい比較の3問。

独自の質問を比較する場合は `--question` を繰り返す。

```bash
uv run python -m app.benchmark \
  --models gemini-3.5-flash-lite gemini-3.1-flash-lite \
  --question "LoRAとは何ですか？100字程度で説明してください。" \
  --question "RAGとファインチューニングの違いを500字程度で説明してください。" \
  --repeat 3 --interval 15 \
  --temperature 1.0 --max-output-tokens 2048 \
  --output results/lec01-custom.csv
```

`--interval` は前の応答終了から次の呼び出しまでの待ち時間。既定の15秒で制限を回避できる保証はない。AI Studioの上限に合わせて調整する。CSVの保存先を省略すると、`results/benchmark-<UTC日時>.csv` に保存する。既存ファイルは上書きしない。

## 計測値の意味

| CSVの列 | 意味 |
|---|---|
| `started_at` | 呼び出し開始時刻（UTC） |
| `model` / `model_version` | 指定したモデル名／APIが返した実際のモデルバージョン |
| `question` / `trial` | 質問本文／その組み合わせの試行番号 |
| `temperature` / `max_output_tokens` / `interval_seconds` | 比較に使った生成条件・待ち時間 |
| `elapsed_seconds` | `perf_counter()` で計測した、API呼び出し開始から応答全体の受信または失敗までの秒数 |
| `input_tokens` / `output_tokens` | APIが返した入力／回答のトークン数 |
| `thoughts_tokens` / `cached_tokens` / `total_tokens` | APIが返した思考／キャッシュ／総トークン数 |
| `status` / `http_status` | 成功、APIエラー、通信エラー、本文なしの区別／HTTPステータス |
| `finish_reason` / `answer` / `error` | 終了理由／回答本文／エラーの説明 |

時間には通信、サーバー側の待機・生成、SDKの応答処理が含まれる。クライアントの初期化、次の呼び出しまでの待機、画面表示、CSV保存は含まれない。ストリーミングではないため、最初のトークンが届くまでの時間は測っていない。

比較コマンドでは自動再試行を無効化し、通信タイムアウトを60秒に設定している。429や503も1試行として保存し、次の予定試行に進む。タイムアウトした場合でもサーバー側で処理が進んでいた可能性があり、利用量は不明となる。Ctrl+Cでは完了済み行を残して終了する。失敗を含む実行の終了コードは1、中断は130。

取得できない使用量はCSVでは空欄にする。成功した応答に欠測が1つでもある項目の平均は「不明」と表示し、0として扱わない。思考を行うモデルでは総数が単純な入力＋回答トークン数と一致しない場合がある。キャッシュ分は総数に足し直さない。フィールドの定義は[Google Gen AI SDK](https://googleapis.github.io/python-genai/genai.html#genai.types.GenerateContentResponseUsageMetadata)を参照する。

本文が空の応答とエラーは時間・使用量の平均から除外する。`finish_reason=MAX_TOKENS` で本文がある応答は集計に含めるため、比較前にCSVで確認する。回答が途中で切れていたら出力上限を上げて全モデルを同じ条件で再計測する。

## 無料枠のレート制限との関係

[Gemini APIの公式資料](https://ai.google.dev/gemini-api/docs/rate-limits)によると、主な制限はRPM（1分あたりのリクエスト数）、TPM（1分あたりの入力トークン数）、RPD（1日あたりのリクエスト数）。いずれかの上限に達するとエラーになる。上限はAPIキー単位ではなくプロジェクト単位で、モデルによって異なる。具体的な値は[AI Studio](https://aistudio.google.com/usage?tab=rate-limit)で実行時に確認し、使用モデル・利用枠・確認日時と一緒に記録する。

今回の結果から、次の観点で考察できる。

- **速い応答でもRPMに達する**：履歴なしの短い質問では入力が少なくても、連続で呼び出す回数が多いと制限に達する。単一モデルを直列に呼ぶ場合、平均応答時間を `L` 秒、待ち時間を `W` 秒とすると、長時間の呼び出し頻度の概算は `60 / (L + W)` 回/分。これは実際の制限値ではなく、バーストや他の処理からの利用も考慮が必要。
- **長い入力・会話履歴はTPMに影響する**：入力平均を `I` トークンとすると、上記条件での入力速度の概算は `I × 60 / (L + W)` トークン/分。`app.ask` は会話履歴を再送するので、継続するほど入力数が増える。`app.benchmark` は履歴なしの比較である点に注意する。
- **出力の長さは時間・総使用量に影響する**：出力や思考が多いモデルは応答完了まで長くなる可能性がある。一方、ここでいうTPMは入力なので、出力トークン数をそのまま加算してTPM到達を説明しない。
- **待つだけではRPDを解消できない**：計測回数はモデル数×質問数×反復数。日次上限に達した場合、短い待機では回復しない。RPDのリセットは米国太平洋時間の深夜0時であり、UTCの0時とは異なる。
- **429だけでは原因を断定できない**：CSVの429数と試行時刻・入力長・AI Studioの利用状況を照らし合わせる。エラー時の使用量は不明なので、成功応答のトークン合計をプロジェクトの正確な総使用量とみなさない。429が出なかった場合も、制限がないとはいえない。

## 結果を読むときの注意

同じ生成設定と質問で比較し、平均だけでなく中央値や各試行のばらつきを見る。モデルの呼び出しは反復ごと・質問ごとに交互に行うが、順番は固定している。混雑、通信、キャッシュ、回答の長さ、思考設定やモデルの更新による差が残るため、少数の計測だけでモデル固有の速度を断定しない。

質問で指定する文字数は目安であり、出力トークン数は一致しない。速さとトークン数に加えてCSVの回答内容を読み、講座固有の質問に正しく答えているかも別途確認する。

### 比較から分かったこと

- **モデル間の差**：Q1とQ3では3.1の平均・中央値がともに短かった。Q2では3.1の中央値は短いが、平均は3.5より長くなった。各条件3回で固定順に呼び出した結果なので、常にどちらが速いという結論は出せない。
- **平均と中央値の差**：3.1のQ2は3回で0.746、4.427、0.769秒だった。中央値は0.769秒だが、4.427秒の試行により平均が1.981秒になった。この試行も正常終了しており、遅延を429の発生によるものとは説明できない。通信・混雑などの内訳は測っていないため、遅くなった原因は不明である。
- **出力の長さとの関係**：500字程度を指定したQ3は、100字程度を指定したQ1より出力が多く、両モデルとも平均応答時間が長かった。一方、3.1では出力が少ないQ2の平均がQ3を上回った。生成する量以外にも時間を変動させる要因があり、出力トークン数だけで時間を決められない。
- **正確さは別に確認する**：3.5のQ2・試行1は「操作・活用」「応用・展開」「変革・創出」と回答した。用語集の [homework-levels](../../data/glossary.json) の定義は「基礎」「実装」「発展」で、どれか1つに取り組めば完了である。正常なAPI応答や速い回答でも、内容が正しいとは限らない。

### 今回の無料枠利用とレート制限の考察

無料枠で、各応答の終了後に15秒待機し、モデルを交互に呼び出した結果、429は18回中0回だった。今回のCSVの開始時刻を使い、各時刻から過去60秒の区間で集計すると、モデルごとの最大呼び出し数は2回、入力トークン数の最大合計は50だった。各モデルの今回のリクエスト数は9回、入力合計は198トークンである。これらはこの計測内の観測値であり、プロジェクト全体の利用量やサービス側の実際の集計窓を再現した値ではない。

公式資料では、制限は主にRPM、入力TPM、RPDに分かれ、モデル・利用枠に応じて異なり、プロジェクト単位で適用される。具体的な上限はAI Studioで確認する必要がある。[Gemini APIのレート制限](https://ai.google.dev/gemini-api/docs/rate-limits)

このため、今回分かったのは「この入力長・頻度・18回の計測では制限エラーが出なかった」ことまでである。具体的な上限値は未確認なので、残りの利用可能量や、15秒待てば必ず安全という判断はできない。

待機を短くすれば単位時間のリクエスト数が増え、RPMに達しやすくなる。会話履歴や長い資料を送れば、同じ回数でも入力TPMの消費が増える。反復数を増やせばRPDの消費も増え、短い待機では日次上限を解消できない。今回は429が出るまで呼び出す実験は行っていないため、上限到達時の挙動や回復までの時間は未測定である。

### 確認したこと

CSVの18行について、モデル×質問×試行番号の重複がないこと、各条件3行ずつあること、生成条件の一致、入力・出力・総数の欠測がないことを確認した。CSVから別途再計算した平均・中央値は、比較コマンドの集計と小数点以下3桁で一致した。
